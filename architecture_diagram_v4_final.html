Job Processing System — V4 Final Architecture

Generated from codebase · 4 services · Postgres + Redis · transactional outbox · idempotent consumer

Services — four independent processes

Service 1
API
cmd/api/main.go · :8080
POST /jobs — atomic dual-write
BEGIN TX
  INSERT jobs (pending)
  INSERT outbox (job.created)
COMMIT → 202
GET /jobs/{id}
SELECT FROM jobs → 200/404
GET /healthz
Service 2
Publisher
cmd/publisher/main.go
loop every 1s
BEGIN TX
  SELECT outbox
    WHERE published_at IS NULL
    FOR UPDATE SKIP LOCKED
    LIMIT 100

  for each event:
    LPUSH jobs:pending
    LPUSH events:pending

  UPDATE published_at = now()
COMMIT
crash before UPDATE → event republished next loop → at-least-once
Service 3
Worker
cmd/worker/main.go
Dispatcher
BLMOVE jobs:pending
    → jobs:processing
send jobID to channel
Worker pool × N (default 5)
UPDATE jobs status=processing
run AI agentic loop
  (tool calls, multi-step)

on success:
  UPDATE jobs completed
  LREM jobs:processing

on failure:
  retry_count++, backoff 2^n
  UPDATE jobs pending
  LREM jobs:processing
Reaper (every 60s)
SELECT processing
  WHERE updated_at < now()-300s
UPDATE pending, retry_count++
LREM jobs:processing
Service 4
Consumer
cmd/consumer/main.go
loop
BLPOP events:pending (5s timeout)

decode EventEnvelope:
  {event_id, event_type, job_id}

INSERT processed_events
  ON CONFLICT → skip

if inserted: log processed
if conflict: log duplicate
PK constraint enforces idempotency — at-most-once processing of duplicate events

Shared infrastructure — coordination through state stores

Source of truth
PostgreSQL
jobs
id · payload · status · result · error · retry_count · retry_after
written by: API (create), worker (state + result), reaper (stuck recovery)
outbox
id · event_type · payload · created_at · published_at
written by: API (insert), publisher (mark published). partial idx on unpublished.
processed_events
event_id (PK) · processed_at
written by: consumer. PK constraint = idempotency mechanism.
Delivery layer
Redis
jobs:pending
list of job IDs waiting to be claimed
LPUSH by publisher · BLMOVE by dispatcher
jobs:processing
list of job IDs currently claimed
BLMOVE target (atomic claim) · LREM by worker on terminal state
events:pending
list of event envelopes for consumer
LPUSH by publisher · BLPOP by consumer

External dependency

External API
Anthropic API · claude-sonnet-4-6
called by worker agentic loop · rate limited · retryable vs permanent error classification

Graceful shutdown

SIGTERM / SIGINT → signal.NotifyContext() cancels each process's context
API <-ctx.Done()
srv.Shutdown()
drain in-flight HTTP requests
Publisher <-ctx.Done()
poll loop exits
current batch commits or rolls back cleanly
Consumer BLPOP returns context error
loop returns nil
Worker <-ctx.Done()
close channel
workers finish current job
wg.Wait()

Data flow summary

FLOW 1
Job creation — atomic
Client → POST /jobs → API → [BEGIN TX: INSERT jobs + INSERT outbox] → COMMIT
FLOW 2
Event relay — at-least-once
Publisher → SELECT outbox (SKIP LOCKED) → LPUSH jobs:pending + LPUSH events:pending → UPDATE outbox.published_at → COMMIT
crash before UPDATE → event republished next iteration
FLOW 3
Job processing
Dispatcher → BLMOVE jobs:pending → jobs:processing (atomic claim) → channel
Worker → AI loop → UPDATE jobs (completed/failed) → LREM jobs:processing
FLOW 4
Stuck job recovery
Reaper → SELECT processing where stuck > 300s → reset to pending → LREM jobs:processing
FLOW 5
Event consumption — idempotent
Consumer → BLPOP events:pending → INSERT processed_events ON CONFLICT SKIP
duplicate event → PK violation → skip + log
FLOW 6
Job status polling
Client → GET /jobs/{id} → SELECT FROM jobs → 200 {status, result, error}
